Dcoker storage:
------------------------------------------------------------
1. docker container read-write thin layer (temporary)
when docker container is removed the thin layer is also gone along with all data
just stopping the container does not remove the file system

2. mounts
	- docker volume/volume
		its controlled by docker 
		it will not be present in the host machine file system
		container removal has no effect on those volumes until and unless you remove the volume 
		a. manually or 
		b. while creating and running a docker container using flag --rm. --rm flag if used, when container is stopped it will be removed automatically too. (in case of anonymous volumes)

		types of volumes
			- named volume
			- anonymous volumes: created every time you create a new container (even with same image). this also can be shared with another.
	
	- bind mount
	- temporary file system (tmpfs)

network:
---------------------
1. containerized app to www -> yes (no restriction)

2. from outside docker (host machine) to a containerized app in docker (map internal port number of containerized app from inside docker to the host machine port using -p flag, ex. -p 3000:3000)
	
3. containerized app to containerized app in the doccker
	- using the container IP address (which is not guaranteed to be stable)
	mongodb://172.18.0.2:27017/swfavorites

	- create a docker network, connect all containerized app to the same and then use the container name as IP address (domain name), since docker network exposes the containerized apps through DNS names, same as that of the container name
	mongodb://<mongodb-container-name>:27017/swfavorites

4. containerized app to any service running on local/host machine: 
	use in the code "host.docker.internal:<port>"
ex: mongodb://host.docker.internal:27017/swfavorites

kubectl


type determines how the Service is exposed. 
Defaults to ClusterIP. 
Valid options are 
	ExternalName, 
	ClusterIP, 
	NodePort, and 
	LoadBalancer. 
"ExternalName" maps to the specified externalName. "ClusterIP" allocates a cluster-internal IP address for load-balancing to endpoints. Endpoints are determined by the selector or if that is not specified, by manual construction of an Endpoints object. If clusterIP is "None", no virtual IP is allocated and the endpoints are published as a set of endpoints rather than a stable IP. "NodePort" builds on ClusterIP and allocates a port on every node which routes to the clusterIP. "LoadBalancer" builds on NodePort and creates an external load-balancer (if supported in the current cloud) which routes to the clusterIP.
